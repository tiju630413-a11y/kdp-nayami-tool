# 工程4: review_loop — 多観点自問自答レビュー（prompts/04_review_loop.md）

一発OK品質の中核工程。7観点で原稿を批評→改稿→再批評を繰り返す。
**収束条件: 重大指摘ゼロ。最大3周（settings.yaml の max_review_loops）。
3周で収束しなければ人間にエスカレーションする。**

## 実行の構造（コンテキスト分離・必須）

観点は**それぞれ独立したコンテキストで実行する**。同一の会話で全観点を
続けて演じることは禁止（自分の直しを見て指摘が甘くなる収束バイアスのため）。

手順（pipeline.py が半自動化する。手動でも同じ流れ）:
1. `python3 scripts/pipeline.py review NNN --round R` を実行すると、
   `books/NNN_*/reviews/round{R}/` に観点別の指示書
   `{観点キー}_task.md` が7枚生成される
2. 各指示書を**新しいセッション（またはサブエージェント）に1枚ずつ**渡して
   実行し、結果 `{観点キー}_findings.md` を同ディレクトリに保存させる
3. 7観点すべての findings が揃ったら、**改稿担当**（これも観点とは別
   コンテキスト推奨）が指摘を統合し、重大指摘を全て潰す改稿を行う
4. `python3 scripts/pipeline.py review NNN --round R --collect` で
   重大指摘数を集計。0なら収束、残っていれば R+1 へ

## ベースライン生成（AI代替判定の前提・round 1 の前に1回だけ）

**レビュアー自身に「AIならこう答えるだろう」を書かせてはならない**
（無意識に弱く書いて自著を通す藁人形化が起きる）。必ず実生成する:

1. **履歴なしの新しいコンテキスト**（このプロジェクトのファイルを一切
   読ませない素のセッション）を開く
2. 素のプロンプトを1つだけ与える:
   「{本書のテーマの悩み}について、解決のための実践的なアドバイスを
   4000字程度で書いてください」
   （テーマは plan.md の pain を1〜2文に要約したもの。本書の構成・断言・
   フレームワークは一切伝えない）
3. 出力をそのまま `books/NNN_*/baseline.md` に保存する（編集禁止）

## 7観点の観点表

| キー | 観点 | 見るもの | 重大指摘の基準（これに該当=重大） |
|---|---|---|---|
| beginner | 初心者読者 | ついていけない箇所・置いてけぼり感 | 前提知識なしで再現できない手順がある / 専門用語が言い換えなしで使われる / 章の冒頭で迷子になる / **「はじめに」の約束と各章の手順が矛盾する**（例: 瞬発力不要と約束したのに即興を要求する手順） |
| harsh_reviewer | 辛口Amazonレビュアー | style/review_checklist.md の**全項目**を適用 | チェックリストのいずれかが FAIL |
| editor | 編集者 | 構成の重複・冗長・章間バランス・タイトル回収 | 同じ主張の章が2つある / 言い換えによる水増し節がある / タイトル回収対応表に穴がある / 章の字数が計画から±30%超 |
| fact_checker | 事実確認者 | 医療・法律・金銭の断定、危うい一般化 | 診断的表現がある / 専門家誘導定型文が該当章にない / 出典のない統計・断定的な因果がある |
| style_guard | 文体番人 | AIっぽさ・style/guide.md 逸脱 | ng_phrases 該当が残っている / 声が章によって別人 / 章冒頭が一般論から始まる / 説教調（命令形連発） |
| ai_substitute | AI代替判定 | baseline.md との比較 | 固有事例・断言・命名FW・実行装置の4面のうち1面でも baseline を明確に上回れない章がある |
| jp_quality | 日本語品質番人 | japanese_quality_prompt.md の四軸（漢字水準・誤用・自然さ・仕上げの精度） | 軸1（漢字上限＝実用書:準2級/小説:2級 を超える難読漢字を開いていない）/ 軸2（ら抜き・さ入れ・主述のねじれ・二重敬語・慣用句の誤用・重言・表記ゆれ）/ 軸3（同長文3連続・段落頭の接続詞連発・同一語尾4連続・AI常套句・句読点や！？の過剰・AI的な二重引用符""）/ 軸4（一文一義・指示語の多用・近接の同語反復・カタカナ語の乱用・表記統一）のいずれかで「要修正」がある |

## 観点別指示書の共通フォーマット（pipeline が生成する内容）

各指示書は自己完結する（受け手は他の観点の存在も、何周目かも知らなくてよい）:

```markdown
# レビュー任務: {観点名}

あなたは{観点の人物設定}です。以下の原稿を批評してください。
あなたの仕事は褒めることではなく、出版を止める欠陥を見つけることです。
指摘ゼロで返すのは、全文を検査し尽くした場合だけにしてください。

## 読むもの
- 原稿: books/NNN_*/draft/ 以下の全章
- 判定基準: {観点ごとの参照ファイル}

## 重大指摘の基準
{観点表の基準をそのまま転記}

## 出力形式（books/NNN_*/reviews/round{R}/{キー}_findings.md）
| # | 重大/軽微 | 章 | 該当箇所（引用10-30字） | 指摘 | 修正の方向 |
最後に1行: SEVERE_COUNT: {重大指摘の数}
```

### ai_substitute 観点の追加指示

- `baseline.md` と原稿を章ごとに突き合わせ、次の表を必ず作る:
  | 章 | 固有事例 | 断言 | 命名FW | 実行装置 | 判定 |
  各セルは「baselineに無い要素の有無と質」を○△×で。×が1つでもある章は重大指摘
- 上回れない章への修正の方向は「著者資産の追加注入」を第一候補にする
  （data/author_assets/assets.json の未使用資産から候補IDを挙げる）

### jp_quality 観点の追加指示

- 基準は `japanese_quality_prompt.md`（唯一の参照元）。指示書には、この本の
  ジャンルと漢字上限（実用書＝準2級／小説＝2級。book.json の genre で決定）が
  自動で差し込まれる
- findings 表の前に、三軸の判定を必ず記載する（各 合格／要修正）:
  漢字水準／誤用／自然さ
- 各指摘は「該当箇所の引用・軸（漢字/誤用/自然さ）・問題・修正案」を含める。
  「要修正」が一つでもある箇所は重大指摘として SEVERE_COUNT に数える
- 直しは原文の意図・雰囲気を壊さない範囲にとどめる（過剰な書き換えをしない）

## 改稿担当への指示

- 重大指摘は全て潰す（反論がある場合は findings に返信を書き、人間の判断へ）
- 軽微指摘は採否を判断してよいが、採否と理由を1行ずつ残す
- 改稿は draft/ を直接更新し、`reviews/round{R}/revision_notes.md` に
  「指摘# → どう直したか」の対応表を書く
- 改稿で新しい資産を使ったら assets_used.json を更新する

## 収束と記録

- 全観点の SEVERE_COUNT 合計が 0 → 収束。`reviews/converged.md` に
  周回数と最終状態を記録
- 3周で収束しない → `reviews/escalation.md` に「残った重大指摘・
  改稿担当の見解・人間に判断してほしい点」を書いて停止
- 全周のログは reviews/round{R}/ にそのまま残す（仕様§5: logs はここを指す。
  pipeline が logs/reviews_NNN.md にサマリを転記する）
